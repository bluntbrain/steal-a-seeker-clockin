I

The short version

The game is not slow because the engine is wrong. The simulation already runs on the UI thread at a fixed 30 ticks per second and the browser build holds 120 frames per second. The weight is in three other places: the app is big and starts slowly, every server call takes half a second because the server is on the wrong side of the planet, and the first tap after a level loads still does a lot of work before anything moves. Those three are fixable inside the current stack in days, not weeks.

Switching engines would not help before the Clock In deadline on 8 October 2026 and would throw away the one thing that makes the leaderboard trustworthy: the same TypeScript simulation runs on the phone and on the server to verify every score. Section IV explains the trade in plain words.

Bosses and backend levels are a design problem, not a speed problem. Today a boss is a normal guard with more health and a name tag, standing in a room with four open courts. Sections V to VII lay out boss arenas, boss presentation, how the backend already makes levels, how to add more by running one command, and a new level generator that builds mazes with corners and pockets like the reference game.

What to do first

1. Move the API to Singapore or Mumbai (one Railway setting, an hour). 2. Turn on code shrinking and drop the 3D phone viewer from the game build (a day, saves about 30 MB and most of the start time). 3. Acknowledge every tap on the very next frame (a day). 4. Build the maze generator and boss arenas (three to four days, needs a rules revision and a server deploy).

II

Where the time goes today

Think of the game as four rooms in a factory. The engine room is the simulation: guards, cones, hearing, your courier. The paint shop draws it with Skia. The warehouse holds the art, music and native libraries that ship inside the APK. The post office talks to the server. Each has a different bottleneck.

The one number we do not have

No real phone has ever been profiled. The emulator cannot measure frame rate (it has no GPU) and exaggerates start time. The first task in any speed work is to install the APK on the Seeker, play level 1 and a crowded level for two minutes each, and record frame times with Android's own tools. Everything else in this plan is ordered by how likely it is to matter on that device.

IV

Would switching technology make it smoother?

Honest answer: not before the deadline, and probably not at all for this game. Here is the comparison in plain words.

Why the engine is not the bottleneck

Smoothness in this game has three parts. The simulation already runs on the UI thread in Reanimated worklets at a fixed 30 ticks per second, so JavaScript garbage collection on the main thread cannot stutter it. The drawing is Skia, the same library Chrome and Flutter paint with; the walls, floor and rails are recorded once per level and replayed, so a frame mostly draws a handful of sprites and cones. The browser build, which uses the same code, holds 120 frames per second with a 95th percentile frame of 8.4 milliseconds. The feel is input latency and start time, and neither depends on the engine.

What a Unity or Godot rewrite would buy is consistency on weak hardware and better tooling for effects. What it would cost is the deterministic shared simulation: the server replays every submitted run with the same TypeScript the phone ran, and that is what makes the total-points leaderboard honest. Rebuilding that twice, in two languages, bit for bit, is the real price, and it is far larger than the engine swap itself.

Smaller swaps that are worth it

  • Drop Filament. It is a full 3D engine carried for one menu widget. Pre-rendered turntable frames look the same and remove 22 MB plus a native library from start.
  • One Solana library. Keep kit, drop web3.js and the 9.4 MB crypto library it drags in. Smaller app, faster wallet screen.
  • Nothing else. React Native 0.83 with the new architecture, Hermes bytecode and Skia 2.4 are current. Upgrading for its own sake adds risk during the deadline week.

Making a boss feel like a boss

Today a boss is a warden with extra health, a 12 percent bigger sprite, a name under the health bar and a two second entrance card. The room is a normal template with four open courts. The screenshots below are level 15, Toly, taken in the web preview on 5 October.

A boss needs a stage, a signature, a health drama and a payoff. None of those are in the room templates or the renderer today, and only the first two need the simulation to change.

VI

How levels after 12 are made, and how to add more

Levels 1 to 12 are hand authored. From 13 onward a level is a recipe: a few numbers that pick a room template, a mirror and flip, a seed, a guard roster and a modifier. The recipe is tiny; the server builds the full level from it, proves it can be won with a solver, checks that proof with the same verifier that checks player scores, and only then stores it. Rows never change after publish, so a level plays identically for everyone forever.

Adding more levels today

Right now adding levels is one command run from a laptop with the production database address in the environment. It publishes the next contiguous batch, writes a receipt under verification/campaign-levels/, and the phones pick the new levels up the next time the Hideout opens. No app update is needed.

# dry run: build and solve 101 to 150 without touching the database
DATABASE_URL=<production url> npx tsx scripts/publish-campaign-levels.ts --to 150 --dry

# publish for real (levels must be contiguous; existing rows are never changed)
DATABASE_URL=<production url> npx tsx scripts/publish-campaign-levels.ts --to 150

Three rules protect players. Levels are published as one contiguous run, so there is never a gap on the map. A published row is immutable; if a room template changes later, old levels still play the old geometry. The command refuses to run if the rules hash in the repository is not the one the server is pinned to, so a level can never be published that the server cannot verify.

VII

Better backend levels: corners, pockets and mazes

The reference levels from Hunter Assassin share a grammar. Thick brick walls form a maze with corridors about one character wide. Every three or four tiles there is a corner, so no guard sees far. Dead-end pockets give you a place to wait. Crates sit at corridor mouths as low cover. Lasers, keyed doors and medkits are placed on the main route to force choices. The map is dense: roughly 40 percent of the floor is wall.

Our ten templates are the opposite shape. They are open courts with islands: 13 to 15 boxes, about 16 percent wall, and sightlines that cross half the room. The guard engine from revision 17 (patrol loops, long cones, hearing, body discovery) is tuned for hiding, but the rooms give you little to hide behind.

What the generator must guarantee

PropertyTargetHow it is checked

What changes in the code

  • shared/campaign-levels.ts: recipe version 3 with a maze block (grid, braid ratio, pockets, gates). Version 1 and 2 recipes keep building exactly as before, so published rows stay valid.
  • shared/maze-rooms.ts (new, about 150 lines): carve, braid, thicken, place crates and gates, measure coverage and sightlines. Pure functions, seeded, no randomness outside the seed.
  • Lasers and key doors exist as mechanics in the authored levels (tripwires, switches); the generator reuses those blocker kinds. No new rule is needed for a laser gate; a key door that opens the exit on pickup is a small rule and goes in the same revision as the boss phases.
  • Art: the ribbed wall caps regenerated this week already read as thick slabs; mazes need a crate sprite per district (three images) and a laser emitter sprite.
  • Difficulty: bands map to coverage, guard count and gates; the roster logic in makeCampaignRecipes stays.
Cost of a rules revision

Boss phases, exit-on-kill and key doors change the simulation. That means revision 18: generate the bundle, pin revision 17 for existing levels, add compatibility tests, deploy the API before the APK, and publish the first maze batch after the deploy. Rendering and audio changes need none of this and can ship any time.

VIII

Order of work

Grouped so that the deadline week ships only safe changes, and the simulation revision follows once it is measured and tested.

  • Day 1, measure. Install code 47 on the Seeker. Record start time, frame times on levels 1 and 24, memory after ten scene changes. Move the Railway service and database to Singapore or Mumbai. Add the CAMPAIGN_TARGET_LEVEL boot publish.
  • Day 2, lighter app. R8 minify and resource shrink on a QA flavour; wallet smoke test. Drop Filament for the turntable renderer. Server calls off the start path.
  • Day 3, feel. Tap acknowledged on the next frame. Floor as one draw, alarm layers into Skia, fewer rays for far cones. Boss size, shadow, health band, signature tells, entrance copy, defeat stinger.
  • Days 4 to 5, rooms. Maze generator with metrics and the three boss arenas as templates. Dry-run publish of 101 to 150 and read the receipts. Review the first twenty rooms by eye in the web preview.
  • Days 6 to 7, revision 18. Boss phases, exit-on-kill, key doors, pathfinding caches. Bundle, compatibility tests, API deploy, then the APK, then publish the maze batch.
  • After. Weekly cron for ten new levels. One wallet library. Decide on the GPU sprite batcher only if the Seeker frame times still miss 16 ms.
