Execution proposal · 4 October 2026 · no stream or agents started

Make the game responsive.
Then make AI runs worth watching.

Ship the current APK first. Measure real phone performance before changing the engine. Prove a one-hour AI competition is watchable before paying to keep it live all day.

The business test: a 24/7 feed is distribution inventory, not a reason to watch. A visible challenge, different strategies, short rounds, close escapes and a score to beat give it a purpose. Judge the pilot by watch time and new players, not hours broadcast.

1. What the code already does

Current source uses Expo / React Native, Reanimated worklets and Skia for the 2D game. It already runs a fixed 30 Hz simulation with interpolated rendering, limits catch-up to three ticks, publishes HUD state roughly every 120 ms, and coalesces repeated taps with an 80 ms interval. Campaign artwork is rendered in virtualized FlatList scenes. Sprites were previously converted to WebP, cones moved to simulation ticks, and native audio writes reduced. These are existing features, not proposed optimizations.

The expensive-looking paths still need measurement: grid search plus nested path smoothing in src/game/navigation.ts; 33 visibility rays per active guard per tick in src/components/GuardLayer.tsx; full game snapshots sent to JS in src/GameScreen.tsx; and three world images decoded eagerly in src/components/CampaignMap.tsx. Code inspection identifies candidates, not proven current bottlenecks.

Proposed acceptance targets, not achieved results: sustained 60 Hz presentation with at least 95% of frame intervals ≤20 ms, fewer than 1% above 33 ms, no recurrent stalls over 100 ms, cold start to usable UI under 3 s, and no progressive memory growth across a 20-minute session. Keep a stable 30 fps reduced-effects fallback only if the device measurements justify it. A 60 fps display budget is about 16.7 ms; see React Native performance guidance.

Do not start with an engine rewrite. The current architecture already separates simulation and rendering. First fix the measured worst spikes. Increasing courier speed would change difficulty, not resolve dropped frames.

3. The AI show: “Three thieves. One Seeker.”

Ghost

Prioritizes cover, waits for openings and tries to finish with full health. Measured on clean escapes.

Rush

Takes short routes and aggressive knife opportunities. Measured on time and survival.

Collector

Trades time for guard takedowns and coins, then tries to escape. Measured on the actual game's score.

Run the same map and seed sequentially for all three, rotate the order, show a comparison after each round and advance through levels 1–5 initially. Run one visible agent at a time. A human can try the same challenge later. Keep bot scores in a separate exhibition board so they cannot crowd out real players or earn campaign credits.

4. How the agents play

Game observations→Strategy planner→Validated action→Existing input pipeline→Real simulation + replay

Recommended: a hybrid controller. A language model chooses a short strategy or waypoint when a run starts, a route fails, the courier is spotted, or the phone is collected. A fast deterministic controller handles movement and attack timing between those decisions. Do not request a language model decision every frame: it adds latency and cost without useful control.

  • Add a demo-only observation adapter with the courier's position, health, carrying state, known geometry, visible guards and public objectives. Do not expose hidden guard intentions, unrevealed positions or future RNG. Describe it honestly on screen as “LLM strategy · scripted controls”, not an AI learning purely from video.
  • Use typed, allowlisted commands that map to existing move / target / wait controls. Validate coordinates, target IDs and command rate; feed the normal simulation and recorder. The agent cannot set health, teleport, alter guard state or claim a win.
  • Add timeouts, retries with backoff and a deterministic fallback. Show when fallback control is active. A model outage must not freeze the game.
  • Keep current goals and a short failure summary between rounds. This is prompt memory, not model training; do not claim the bot “learns” through weight updates.
  • Record actions, observed state, seed, rules hash, replay and result. A screen-only vision agent can be a later benchmark segment; it is a slower, more expensive first implementation.

Scope isolation: use a separate stream build and local/exhibition data store. Production score and reward endpoints must reject exhibition sessions, or the runner must have no authenticated route to them. No production wallet, purchase flow or private key belongs on the streaming machine. A client-only “demo” label is not sufficient isolation.

5. Streaming stack

Dedicated always-on computer → game web build in a visible browser → OBS window/audio capture → RTMPS → X Live Studio. Keep the browser visible and awake; background-tab throttling can disrupt game timing. Start with an existing spare machine before renting a GPU server. The current game can render in the browser, avoiding a phone emulator for the first show.

Use a 16:9 canvas at 1280×720, with the portrait game large in the center and compact agent, goal and scoreboard panels on either side. Start at 30 fps for the encoded stream while the game renders at 60. Use the game's existing music and effects with lower music gain under event commentary. Add brief event-based captions first; optional ElevenLabs speech later, with limited calls and cached lines. Avoid constant narration.

X Live Studio currently supports external RTMP sources and private test broadcasts, and limits each livestream to 24 hours. A timed-out broadcast must be recreated. Its documented keyframe interval is three seconds. Verify the actual account's Live Studio access and encoder settings before purchasing infrastructure. Older Producer documentation mentions six-hour limits; use the current Live Studio settings.

A watchdog can control scenes and reconnect through OBS's built-in WebSocket interface. Keep its control port local and authenticated. OBS reconnection does not create the next X broadcast: broadcast rollover needs a separately tested, supported account workflow. Do not promise uninterrupted unattended X operation until that part is verified. Schedule a new session before the duration limit, test the transition and accept a short visible break if necessary.

6. Reliability and spending limits

FailurePlanned response
Agent stuck or run over timeDetect lack of progress while distinguishing intentional waiting; try a new route, then restart after a bounded timeout. Log the failure and move to the next agent.
Game or browser crashSwitch OBS to a clearly labeled recovery scene, restart the runner, restore the next round from disk. Never loop an old clip and label it live gameplay.
Model unavailable or spend cap reachedStop model calls; continue with the disclosed deterministic baseline or pause the show. Store daily token/call totals and enforce the cap before sending requests.
Network / encoder failureBounded reconnect, dropped-frame and bitrate monitoring, alert the operator. Recreate an ended X session through the supported workflow; do not retry blindly forever.
Unbounded recordings / memoryRotate logs and clips; keep selected highlights and replay files, cap disk usage. Soak-test process memory, browser GPU memory and file handles.

Budget model: 24-hour hosting + X access if required + model input/output tokens + optional speech. One planner call every 30 seconds would already mean 2,880 calls/day for one active agent; three simultaneous agents would triple that. Event-driven calls, compact observations and one active agent keep costs bounded. Measure the one-hour pilot and extrapolate from actual usage before setting a daily spend cap. At an illustrative 6 Mbps output, video alone sends about 64.8 GB/day; verify upload and hosting egress limits. These are planning calculations, not provider price quotes.

7. Delivery sequence and decision gates

  1. Performance baseline and top fixes — estimate 2–3 engineering days. Physical Seeker traces first, one optimization at a time, deterministic replay checks. Keep the accepted rules version stable unless a gameplay change is intentional.
  2. Exhibition runner — estimate 1–2 days. Observation / action adapter, three strategies, separate scores, replay logging, restart loop. Run 100 attempts without unattended crashes; track completion and stuck rates.
  3. Watchable pilot — estimate 1 day. Overlay, music mix, captions, OBS scene control. Private 30-minute stream, then a scheduled public one-hour challenge after approval.
  4. Reliability — estimate 1–2 days plus elapsed testing. Deliberately kill the browser, disconnect the model and interrupt networking. Run a six-hour soak, then a full 24-hour trial including broadcast rollover.
  5. Scale only after evidence. Compare pilot watch time, returning viewers, game visits / downloads and extracted clips. Choose a target before the pilot. If people leave quickly, improve the format or run scheduled competitions instead of paying for an empty 24/7 feed.

Estimates assume one engineer and existing device/account access; they are not deadlines. The next action I recommend is the real-device performance baseline, followed by a single-agent local prototype. No stream subscription, cloud machine, AI generation or public broadcast has been started by this plan.
